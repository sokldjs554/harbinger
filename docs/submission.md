# 점검 기록에서 다음에 확인할 설비까지

최종 기술·배포 기준은 [PR #16 병합·검증 기록](verification/closeout-20261027/README.md)이다. 소스 `e33072b`, AWS 실제 계산 모델 `v20261026-151241`, Pages 저장 모델 `v20261026-093937`, 특징 정의 3·116개로 확인했다. 2026-10-27 KST에 기록을 대조했다. 이 문서는 포트폴리오 원고이며 제출 완료를 뜻하지 않는다. 제품 방향·기술 범위 선택·검토 의견 전달·결과 확인은 사용자 역할이고, 세부 구현·실험·문서화에는 Codex 지원을 사용했다.

## 소개 문장

시설 점검 기록을 검증하고, 우선 확인할 설비와 원문 근거를 제공하는 분석 웹을 만들었습니다. 기존 평가에서 학습·보정 경계 이후의 정답을 사용하는 문제를 재현한 뒤 시간 경계와 생존 관측 기간을 수정했고, 같은 합성 데이터로 성능 감소까지 공개했습니다. CSV 업로드부터 FastAPI 모델 계산, 과거 결과 비교, 고객사 보류 평가, 보고서 다운로드까지 한 흐름으로 구현했습니다. AWS EC2에 HTTPS로 배포하고 실제 CSV 처리, 재부팅 후 기본 모델 복구, 인증서 갱신 시험을 검증했습니다.

회사 실제 데이터를 받거나 고객 실증을 수행한 프로젝트는 아닙니다. 공개 제품 맥락에 맞춰 만든 합성 데이터 포트폴리오입니다.

## 기록을 쌓은 다음의 판단을 돕고 싶었습니다

시설 점검 문제를 고른 이유는 기록을 조회하는 기능에서 한 단계 더 나아가, 다음에 확인할 대상을 고르고 그 근거를 되짚는 과정을 만들고 싶었기 때문입니다. 설비 이력·점검 판정·메모를 한 기준일에 맞춰 분석하고, 사용자가 원문과 예측을 함께 확인하는 흐름을 설계했습니다. 문제 정의는 [공개 회사·제품 조사](company-research.md)를 바탕으로 했으며, 현장 인터뷰로 수요 규모를 입증한 것은 아닙니다.

## 점수가 낮아져도 비교 기준을 바로잡았습니다

학습·보정 경계 뒤에 발생한 고장이 앞 구간의 정답으로 들어가는 문제를 재현했습니다. 30일 관측 완료 여부와 생존 관측 기간을 구간 경계에 맞춰 수정하고, 같은 성숙 테스트 18,439행에서 다시 비교했습니다. AUROC는 0.7736에서 0.7696으로 낮아졌습니다. 여러 경계·전처리 수정이 함께 반영된 결과이므로 감소 전체를 하나의 수정 효과로 해석하지 않았습니다. [전후 평가와 검증](../README.md#평가-오류-수정과-재측정)

## 평균 뒤에 가려진 조건을 확인했습니다

수정된 사이트 마스킹과 에너지 특징으로 기존 생성 시드 3개 × 학습 시드 2개의 메모 누락 실험을 다시 실행했습니다. 원래 채택 기준을 통과했지만, 선택 정책의 25/50% 누락 평균 개선폭은 +5.297→+5.100%p로 낮아졌습니다. 정상 입력 변화는 +0.170→+0.139%p였습니다. 알려진 시드를 다시 사용한 후향적 검증이며 독립적인 새 고객 성능 입증은 아닙니다. [모든 실행·변동·과거 구현과의 대조](verification/completion-20261026/memo/README.md)를 보존했습니다.

기본 HGB는 별도의 새 합성 시드에서 비교했습니다. 검증 자료에서 기준을 고정하고 전체 특징 모델 유지를 선택한 뒤, 선택에 쓰지 않은 테스트를 계산했습니다. 테스트 평균은 전체 특징의 AUROC 0.772578·PR-AUC 0.257555·Brier 0.066285·상위 10개 적중률 25.8909%, 메모 제외는 0.767690·0.255462·0.066442·25.5212%였습니다. 같은 생성기의 세 세계이고 검증은 보정에도 사용했으므로 한계를 함께 남겼습니다. [동결된 선택과 원시 예측](verification/completion-20261026/default/README.md).

중요도와 필수 점검을 포함한 실제 추천 함수도 같은 후보·예산·필수 조건으로 평가했습니다. 단일 고정 세계의 위험순 상위 10개 적중률 23.8444%와 실제 서비스 목록 적중률 20.3111%를 구분했습니다. 필수 설비가 예산을 넘으면 실제 선택 수와 초과량을 보고하고, 고객사·날짜의 평균과 신뢰구간은 같은 고객사 가중을 사용했습니다. [실제 선택·집계 검증](verification/completion-20261026/technical-results.md).

## 사용자가 멈춘 지점에서 화면을 고쳤습니다

시설관리 동료와 일반 사무직 친구의 검토 의견에서 위치 검색, 과거 예측과 현재 상태의 혼동, 기록 완전성 확인의 어려움을 확인했습니다. 층·구역 검색과 실제 적용 기준일을 표시하고, 자료에 없는 현재 수리 상태는 확인되지 않았다고 안내했습니다. 기록 누락 여부를 모르는 사용자는 확인란을 체크하지 않아도 탐색할 수 있게 했고, 그 경우 서버에서 이후 결과와 성능 평가를 보류하도록 구현했습니다.

수정 후 추가 문제가 없다는 회신을 전달받았습니다. 과업별 재측정 자료는 없어 시간 단축이나 무도움 성공률 개선을 주장하지 않습니다. [사용자 의견과 회신](user-reviews/README.md), [API·브라우저·모바일 검증](verification/usability-20261025/README.md)을 따로 남겼습니다.

## 선택한 모델과 되돌릴 근거를 함께 남겼습니다

현재는 전체 HGB를 서비스하고, 전체·메모 제외 모델과 단순 기준을 같은 조건에서 비교하는 [선택 절차](model-selection.md)를 정리했습니다. 실제 고객의 고장 정의·기록 완전성·점검 예산은 확보 후 확인해야 합니다. 수정 후 PyTorch 반복의 검증 선택은 메모 미사용 3회·누락 대응형 2회·기존 모델 1회였으며 이 선택으로 HGB 기본값을 바꾸지 않았습니다. 고객사별 검증 근거와 정책 활성화·롤백을 저장하고, 추론·보고서·설명에 같은 모델을 연결합니다. 실제 고객별 우수성을 입증한 것은 아닙니다.

운영에서는 계산 슬롯 2개를 유지하면서 최대 4개·10초의 대기열을 적용했습니다. 같은 7,352행 CSV와 로컬 동시 4개 요청 조건에서 분석·업로드·다운로드 각각 성공 2/20→20/20, 429 비율 90%→0%, 서버 오류 0을 확인했습니다. 성공 요청의 p95 지연은 분석 0.348→0.629초, 업로드 2.241→4.463초, 다운로드 0.291→0.787초로 늘었습니다. 전후 성공 표본 수가 2개와 20개로 다르며 AWS 처리량으로 환산하지 않습니다. [원시 부하 결과](verification/completion-20261026/operations/README.md)와 [클론 재현 로그 복구](verification/closeout-20261027/README.md)를 함께 공개했습니다.

사용자는 문제·UI 방향과 기술 범위를 선택하고 지인의 검토 의견을 전달하며 결과를 확인했습니다. 실험 시드·구체적인 채택 문턱 등 세부 설계와 코드 작성·실행·문서화는 Codex 지원을 포함합니다. 사용자가 모든 코드를 혼자 작성했다거나 동일 문제를 독립적으로 해결할 수 있다는 증거로 바꾸지 않습니다. 자기소개서에 반영할 프로젝트 문장은 [지원 문장 개정안](application-update.md)에 정리했습니다.

## 면접에서 확인받을 지점

- **전처리:** 잘못된 날짜·중복·누락·설비 메타 불일치를 이유와 함께 반환한다. 지원 형식과 한도를 계약으로 명시했다.
- **모델링:** 전체 모델 AUROC가 0.7736에서 0.7696으로 떨어졌어도, 미래 정답을 제외한 결과를 채택했다. 메모의 추가 성능 이득이 없는 조건도 공개했다.
- **고객별 검증:** 해당 고객사의 정답을 학습·보정에서 제외한 LOSO와 단순 고객사별 기술통계를 구별했다. 자체 정답 보정도 성숙 기간을 적용한다.
- **서비스:** 업로드별 메모리 세션, 만료·처리 한도, 원문 설명, 실제 모델 비교, CSV/JSON/Markdown 다운로드를 구현했다.
- **검증:** 실패를 재현하는 테스트, 실제 모델 재학습, API 통합·브라우저·컨테이너 실행을 구분해 기록한다. 실행하지 못한 검증을 통과로 적지 않는다.

실행 결과와 공개 배포 상태의 최신 기준은 [검증 기록](verification/README.md)이다. 모델 성능 숫자는 [평가 산출물](../artifacts/)에서 확인할 수 있다.

기존 EC2에 연결한 외부 알림은 [통제 시험](ops/external-alerts.md)으로 장애·복구 전송과 프로젝트 소유자의 두 메일 실제 수신을 확인했다. 사용자는 SMTP 설정 저장과 실제 수신 확인을 했고, 연결·실패 증거 보완·검증·문서화에는 Codex 지원을 사용했다. 제공된 수신 표시 시각은 2026-10-27 02:58 KST(분 단위)이며 개별 전달 지연을 계산하지 않았다. 서버 전체 장애의 독립 감시, 실제 고객 사고 대응, 장기 SLA는 검증 범위 밖이다.
