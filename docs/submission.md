# 점검 기록에서 다음에 확인할 설비까지

## 소개 문장

시설 점검 기록을 검증하고, 우선 확인할 설비와 원문 근거를 제공하는 분석 웹을 만들었습니다. 기존 평가에서 학습·보정 경계 이후의 정답을 사용하는 문제를 재현한 뒤 시간 경계와 생존 관측 기간을 수정했고, 같은 합성 데이터로 성능 감소까지 공개했습니다. CSV 업로드부터 FastAPI 모델 계산, 과거 결과 비교, 고객사 보류 평가, 보고서 다운로드까지 한 흐름으로 구현했습니다. AWS EC2에 HTTPS로 배포하고 실제 CSV 처리, 재부팅 후 기본 모델 복구, 인증서 갱신 시험을 검증했습니다.

회사 실제 데이터를 받거나 고객 실증을 수행한 프로젝트는 아닙니다. 공개 제품 맥락에 맞춰 만든 합성 데이터 포트폴리오입니다.

## 기록을 쌓은 다음의 판단을 돕고 싶었습니다

시설 점검 문제를 고른 이유는 기록을 조회하는 기능에서 한 단계 더 나아가, 다음에 확인할 대상을 고르고 그 근거를 되짚는 과정을 만들고 싶었기 때문입니다. 설비 이력·점검 판정·메모를 한 기준일에 맞춰 분석하고, 사용자가 원문과 예측을 함께 확인하는 흐름을 설계했습니다. 문제 정의는 [공개 회사·제품 조사](company-research.md)를 바탕으로 했으며, 현장 인터뷰로 수요 규모를 입증한 것은 아닙니다.

## 점수가 낮아져도 비교 기준을 바로잡았습니다

학습·보정 경계 뒤에 발생한 고장이 앞 구간의 정답으로 들어가는 문제를 재현했습니다. 30일 관측 완료 여부와 생존 관측 기간을 구간 경계에 맞춰 수정하고, 같은 성숙 테스트 18,439행에서 다시 비교했습니다. AUROC는 0.7736에서 0.7696으로 낮아졌습니다. 여러 경계·전처리 수정이 함께 반영된 결과이므로 감소 전체를 하나의 수정 효과로 해석하지 않았습니다. [전후 평가와 검증](../README.md#평가-오류-수정과-재측정)

## 평균 뒤에 가려진 조건을 확인했습니다

생성 시드 3개와 학습 시드 2개에서 모델 순위, 메모 누락·문자 삭제·기록 지연을 비교했습니다. 전체 HGB의 주간 상위 10개 적중률 평균은 26.33%, 메모 제외 HGB는 26.00%였지만 실행별로는 메모 제외 모델이 6회 중 4회 앞섰습니다. PyTorch text+site는 메모 25% 누락 시 같은 지표가 23.94%에서 17.73%로 낮아졌습니다. 복잡한 모델이나 입력을 더 많이 쓰는 모델을 일괄 채택하지 않고, 기록 품질과 점검 예산을 맞춘 검증으로 선택해야 한다는 판단으로 이어졌습니다. 수치는 모두 합성 데이터 결과이며, [실험 조건과 한계](verification/robustness-20261025/README.md)를 함께 공개했습니다.

## 사용자가 멈춘 지점에서 화면을 고쳤습니다

시설관리 동료와 일반 사무직 친구의 검토 의견에서 위치 검색, 과거 예측과 현재 상태의 혼동, 기록 완전성 확인의 어려움을 확인했습니다. 층·구역 검색과 실제 적용 기준일을 표시하고, 자료에 없는 현재 수리 상태는 확인되지 않았다고 안내했습니다. 기록 누락 여부를 모르는 사용자는 확인란을 체크하지 않아도 탐색할 수 있게 했고, 그 경우 서버에서 이후 결과와 성능 평가를 보류하도록 구현했습니다.

수정 후 추가 문제가 없다는 회신을 전달받았습니다. 과업별 재측정 자료는 없어 시간 단축이나 무도움 성공률 개선을 주장하지 않습니다. [사용자 의견과 회신](user-reviews/README.md), [API·브라우저·모바일 검증](verification/usability-20261025/README.md)을 따로 남겼습니다.

## 고객별 선택에는 다음 근거가 더 필요합니다

현재는 전체 HGB를 서비스하고, 전체·메모 제외 모델과 단순 기준을 고객 자료에서 비교하는 [선택 절차](model-selection.md)를 정리했습니다. 실제 고객의 고장 정의·기록 완전성·점검 예산을 확인하고, 아직 사용하지 않은 미래 기간에서 검증해야 합니다. 자동 고객별 모델 선택과 PyTorch 누락 대응 개선은 완료한 기능이 아닙니다.

프로젝트 방향과 수용 기준은 사람이 정하고 Codex를 활용해 구현·검증했습니다. 사용자 검토를 수집하고 결과를 확인하며 개정한 과정과 실제 생성된 코드·실험 근거를 함께 제시합니다. 기존 자기소개서에 반영할 프로젝트 경험 문장은 [지원 문장 개정안](application-update.md)에 정리했습니다.

## 80초 시연

[녹화 영상](demo/walkthrough.mp4)은 정적 예제 재생 화면의 실제 브라우저 조작입니다. 영상의 모드 표기를 확인하세요. [AWS 데모](https://sokldjs554.github.io/harbinger/live.html)와 로컬 서버에서는 같은 UI로 CSV 업로드와 새 날짜 계산을 수행합니다. [AWS 자동검증 조작 기록 33초](demo/aws-checks.mp4)도 제공합니다.

| 구간 | 조작 | 전달할 내용 |
|---|---|---|
| 0–8초 | 첫 화면 | 점검 기록으로 우선 확인할 설비를 고른다. 예제는 합성이다. |
| 8–19초 | 설비 검색 | 자동문을 검색하고 고객사·종류·정렬로 대상을 좁힌다. |
| 19–32초 | 설비 상세·점검일 선택 | 별도 상세에서 원문과 판단 항목을 연결한다. 기여도는 원인 증명이 아니다. |
| 32–43초 | 과거 검증 | 최근 판정 규칙·로지스틱·현재 모델·메모/이력 제거 모델을 같은 조건으로 비교한다. |
| 43–54초 | 고객사별 결과 | 현재 날짜별 표와 8개 고객사 LOSO 실험을 구분한다. |
| 54–67초 | 최신 기준일 선택 | 이후 30일이 부족하면 성능을 만들지 않고 평가를 보류한다. |
| 67–80초 | 보고서 다운로드 | 모델 버전과 관측 종료, 보류 사유를 함께 남긴다. |

## 면접에서 확인받을 지점

- **전처리:** 잘못된 날짜·중복·누락·설비 메타 불일치를 이유와 함께 반환한다. 지원 형식과 한도를 계약으로 명시했다.
- **모델링:** 전체 모델 AUROC가 0.7736에서 0.7696으로 떨어졌어도, 미래 정답을 제외한 결과를 채택했다. 메모의 추가 성능 이득이 없는 조건도 공개했다.
- **고객별 검증:** 해당 고객사의 정답을 학습·보정에서 제외한 LOSO와 단순 고객사별 기술통계를 구별했다. 자체 정답 보정도 성숙 기간을 적용한다.
- **서비스:** 업로드별 메모리 세션, 만료·처리 한도, 원문 설명, 실제 모델 비교, CSV/JSON/Markdown 다운로드를 구현했다.
- **검증:** 실패를 재현하는 테스트, 실제 모델 재학습, API 통합·브라우저·컨테이너 실행을 구분해 기록한다. 실행하지 못한 검증을 통과로 적지 않는다.

실행 결과와 공개 배포 상태의 최신 기준은 [검증 기록](verification/README.md)이다. 모델 성능 숫자는 [평가 산출물](../artifacts/)에서 확인할 수 있다.
