# 친구·동료와 하는 15–20분 사용성 검토

친구나 동료도 검토 참여자가 될 수 있다. 시설 업무 경험이 없는 참여자에게는 화면 탐색과 설명 이해를 확인하고, 관련 경험이 있는 참여자에게는 실제 역할과 경험 범위 안에서 업무 적합성 의견을 추가로 받는다. **이 문서는 진행 절차이며 검토를 실시했다는 기록이 아니다.** [빈 기록 양식](user-review-template.md)을 참여자별로 복사해 실제 관찰만 작성한다.

| 검토 종류 | 확인할 수 있는 내용 | 구분해서 남길 한계 |
|---|---|---|
| 친구·동료 사용성 검토 | 설비 찾기, 원문 열기, 조건 이해, 업로드·오류·내보내기 조작 | 고객 수요·현장 효과·예측 성능을 입증하지 않음 |
| 시설 업무 경험자 검토 | 경험한 업무에서 근거가 이해되는지, 누락된 조건과 업무 적용 우려 | 직무·경험 범위를 기록. 합성 예제 의견만으로 실제 고객 검증이라고 표현하지 않음 |
| 실제 현장 PoC | 승인받은 실제 기록과 사전 합의한 현장 정책·결과로 효과 비교 | 별도 데이터 적합성·관측 기간·평가 계약이 필요. [실데이터 계획](real-data-checklist.md) 참고 |

친분 여부와 도메인 경험 여부는 별개다. 같은 참여자가 앞의 두 검토를 하더라도 관찰 결과와 경험에 따른 의견을 나눠 적는다.

## 진행 전 준비

- 진행자가 [AWS 실제 계산 데모](https://sokldjs554.github.io/harbinger/live.html) 또는 [로컬 실행](../README.md#실행)을 열어 연결 상태를 확인한다. [저장 예제](https://sokldjs554.github.io/harbinger/)는 탐색용이며 업로드와 새 계산을 지원하지 않는다. 저장 예제만 썼다면 해당 과업은 **미실시**로 남긴다.
- 지원 CSV 양식으로 **합성 예제** 원본과 오류 파일을 준비한다. 오류 파일은 복사본의 점검 행 하나에서 `overall`을 `9`로 바꾸고 나머지 형식은 유지한다. [입력 명세](upload-format.md)를 참고하고 어느 행을 바꿨는지 진행자만 기록해 둔다.
- 합성 자료의 관측 종료일을 확인해 제공한다. 참가자에게 실제 고객 자료를 가져오도록 요청하지 않는다. 승인 없이 고객 기밀을 공유하지 않으며 이 검토에는 합성 자료만 쓴다.
- 별칭, 날짜, 기기, 데모 모드, 소스 버전(확인할 수 있는 경우)을 기록한다. 실제 직업·경험의 상세 기재는 선택이며, 시설 업무 경험 유무는 `있음 / 없음 / 응답하지 않음`으로 기록한다.

검토 전에 다음처럼 안내한다. “서비스 화면을 검토하는 자리입니다. 합성 데이터와 모델을 사용하며 실제 고객 검증은 아직 하지 않았습니다. 막히는 곳과 이해가 안 되는 표현을 알려 주세요. 언제든 중단할 수 있습니다. 메모를 남겨도 될까요?” 화면 녹화·음성 녹음·인용 공개는 각각 별도 동의를 받고, 동의하지 않으면 하지 않는다.

복사해서 보낼 짧은 요청문은 [지인 검토 요청](user-review-invitation.md)에 있습니다.

## 진행 순서

안내·동의 2분, 아래 과업 약 14분, 마무리 2분으로 총 18분을 잡는다. 먼저 영상을 보여주거나 버튼 위치를 가르치면 결과에 영향을 줄 수 있으므로 필요한 사전 설명과 실제로 제공한 도움을 기록한다. 각 과업 시간은 목표 범위이며 시간 초과 자체를 참가자 실패로 단정하지 않는다.

| 과업 | 참가자에게 읽어 줄 요청 | 관찰할 내용 | 예상 시간 |
|---|---|---|---|
| 1. 설비 찾기 | “목록에서 설비 하나를 검색하거나 필터로 찾아 주세요.” | 선택한 설비, 검색·필터 사용, 길을 잃은 지점 | 1분 |
| 2. 원문 확인 | “해당 설비의 점검 원문을 열고 날짜와 내용을 설명해 주세요.” | 원문과 모델 판단을 구별하는지, 날짜 확인, 목록 복귀 | 2분 |
| 3. 기준일 이해 | “예측 기준일을 찾아 주세요. 이 날짜와 이후 고장 결과는 어떤 관계인가요?” | 기준일 이전 입력과 이후 관측 구분, 모르는 표현. 말한 내용을 그대로 기록 | 2분 |
| 4. 새 계산 | “기준일이나 고객사 조건을 바꾸고 결과에 적용해 주세요. 어떤 조건이 적용됐나요?” | 입력값 변경과 계산 적용 구분, 표시된 조건, 대기·오류 이해 | 2분 |
| 5. 합성 CSV 업로드 | “준비한 정상 합성 CSV와 안내한 관측 종료일로 분석해 주세요. 확인 문구가 무엇을 의미하나요?” | 파일 선택·선언 이해·결과 확인. 모델 재학습으로 오해하는지 | 3분 |
| 6. 오류 이해 | “이번에는 오류용 CSV를 올려 주세요. 무엇을 고쳐야 하고 이전 결과는 어떻게 됐나요?” | 실제 오류 문구·행 번호 이해, 회복 시도, 이전 결과 확인 | 2분 |
| 7. 내보내기 | “현재 결과를 원하는 지원 형식으로 내보내고 적용 조건을 찾아 주세요.” | 다운로드 성공, 파일 열기, 기준일·고객사·점검 수 확인 | 2분 |

각 과업은 **도움 없이 완료 / 도움 후 완료 / 미완료 / 미실시** 중 하나로 남긴다. 시작부터 완료 또는 중단까지 걸린 시간을 실제로 재고, 시스템 대기와 진행자 도움을 별도로 메모한다. 먼저 조작을 관찰하고 막힐 때만 필요한 도움을 준다. “쉽죠?”, “현장에서 유용하겠죠?”처럼 답을 유도하지 않는다.

마지막에는 “가장 막혔던 곳은?”, “이 결과로 판단할 수 있는 것과 없는 것은?”, “바꾸고 싶은 한 가지는?”을 묻는다. 업무 경험자에게만 “경험한 어떤 업무에서 검토할 만한가요? 맞지 않는 상황이나 빠진 정보는 무엇인가요?”를 추가한다. 긍정·부정 답변과 판단 불가를 모두 그대로 남긴다.

## 결과 정리와 공개

관찰한 행동, 참가자의 말, 진행자의 해석, 개선안을 분리한다. 참가자 수가 적으면 성공률만 쓰지 말고 실제 인원과 과업별 도움 여부를 함께 적는다. 미실시 항목·중단·서비스 장애도 누락하지 않는다. 수정 후 재검토는 날짜·버전을 구분해 새 기록으로 남긴다.

공개할 때는 동의한 범위에서만 별칭과 실제 검토 유형을 적는다. 참가자·직업·고객·현장 자료·좋은 평가를 만들어 넣지 않는다. **사용성 검토 완료와 실제 고객 PoC 완료는 서로 다른 주장**이다. 미실시 상태에서는 “검토 절차와 기록 양식 준비”까지만 표현한다.

참고 영상도 검토 참여 기록과 구분한다. [33초 영상](demo/aws-checks.mp4)은 **자동 브라우저 검증 조작**, [80초 영상](demo/walkthrough.mp4)은 **저장 예제 설명용 영상**이다. 둘 다 친구·동료 또는 실제 고객의 사용성 검토 증거가 아니다. [기존 실행 검증 기록](verification/README.md)은 당시 기술 검증 이력이다.
