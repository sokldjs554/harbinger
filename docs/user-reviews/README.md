# 사용자 의견에서 화면 개선까지

[시설관리 동료 A 기록](colleague-a.md) · [일반 사용자 B 전달 기록](friend-b.md) · [빈 기록 양식](../user-review-template.md)

두 기록은 사용자가 전달했다. A는 사용자가 잔여 문구의 오기임을 확인한 뒤 정리했다. B는 실제 친구 검토로 전달됐지만 원문에 예시·추가 확인 표현이 남아 있어 시간·발언의 측정/인용 여부를 확정하지 않았다. 두 사람을 모집단으로 일반화하거나 실제 고객 성능 실증이라고 표현하지 않는다.

## 이 검토가 뒷받침하는 내용

친구·동료도 사용자 관점에서 화면과 작업 흐름을 평가할 수 있다. 시설관리 경험자의 의견은 업무 적합성을 검토하는 근거로 활용한다. 예측 성능 검증에는 실제 점검 자료와 그 이후 발생한 고장 기록이 추가로 필요하다. 평가자의 관계보다 **무엇을 사용하고 어떤 결과와 대조했는지**가 구분 기준이다. 현재 기록은 사용성·업무 관점의 의견이며, 실제 현장 자료로 고장 적중을 측정한 결과는 아니다.

## 의견을 반영한 내용

| 의견 | 구현한 대응 | 개발 검증 항목 |
|---|---|---|
| A·B: 설비 번호보다 위치로 찾고 싶음 | 원본의 층·구역을 표시하고 검색에 포함 | 층 검색 결과의 위치, 모바일 ID·위치, 정보 미제공 시 표시 |
| A·B: 지금도 고장인지 알 수 없음 | 점검 당시 판정과 현재 수리 상태를 구분 | 현재 조치 상태는 확인되지 않음; 고장 기록을 완료 작업으로 표시하지 않음 |
| A·B: 과거 예측을 현재 위험으로 오해 | 실제 적용 기준일과 이후 30일 구분 | 날짜 변경 중에도 기존 계산의 날짜 표시 |
| A·B: 변경 즉시 적용되는 줄 앎 | 미적용 상태와 적용 버튼 설명 | 성공 전 결과·내보내기 유지, 되돌리면 미적용 안내 해제 |
| A·B: 누락 여부는 자료 담당자 확인 필요 | 확인 안 해도 탐색 가능; 결과·성능 평가 보류 | API 기본값·세션별 격리·고객별 표·다운로드 보류 |
| B: 영어 열 이름으로 오류 수정 어려움 | 한국어 의미·허용값·헤더 포함 행 번호 | 잘못된 overall 복구, 이전 데이터 보존 |

PDF·담당자·조치 상태 관리는 이번 수정에 포함하지 않는다. 현재 원자료에 없는 담당·완료 상태를 화면에 만들어 넣지 않는다. 목록의 한 줄 원인 설명도 현재 메모를 모델 기여도로 바꾸어 부르지 않는다. 모델 근거는 상세의 실제 기여도와 원문 연결로 확인한다.

## 다시 측정할 때 사용할 도구

[7과업 기록 화면](https://sokldjs554.github.io/harbinger/retest.html)에서 진행자가 도움·미실시·수행/대기 시간을 구분해 JSON을 내려받을 수 있다. [진행·비교 안내](retest-guide.md)에 따라 같은 참가자·모드·시나리오의 전후 기록만 비교한다. 자동 브라우저 검사는 도구 검사이며 사람의 재측정 결과가 아니다. 기존 회신의 불확실성을 소급 해소하지 않는다.

## 수정 후 재검토

2026-10-25 사용자가 수정 후 확인을 요청한 결과를 “물어봤는데 이상 없다고 말해줬어”라고 전달했다. **추가 문제가 없다는 정성적 회신을 전달받았다.** 이를 근거로 문서 정리와 고객별 모델 선택 기준 수립으로 진행한다.

이번 회신에는 응답자별 구분, 실제 확인 날짜·버전·모드, 과업별 수행 결과, 도움 여부, 측정 시간이 포함되지 않았다. 따라서 A와 B 각각의 재검토 완료나 모든 과업의 무도움 성공, 작업 시간 단축을 확정하지 않는다. B의 최초 시간·인용에 남은 불확실성도 이번 회신으로 소급 해소하지 않는다. 실제 고객 성능 실증과는 별개의 기록이다.

아래는 과업별 재검토를 상세히 기록할 때 사용할 절차다. 이번 회신이 이 절차를 모두 수행했다는 뜻은 아니다.

1. 동일한 참가자에게 수정된 버전·모드와 같은 예제 CSV를 제공하고, 이전 사용 경험이 있음을 기록한다.
2. 설비의 층이나 구역으로 찾고 ID를 확인하게 한다. 필터 위치를 먼저 가르쳐 주지 않는다.
3. 상세를 보고 ‘언제의 예측인지’, ‘현장 양호와 예측 확률이 다른 이유’, ‘수리가 끝났는지 알 수 있는지’를 설명하게 한다.
4. 날짜를 변경하고 적용 전·후의 화면과 내려받은 조건을 확인하게 한다. 프로그램이 계산하는 대기 시간을 사용자 조작 시간과 구분한다.
5. 기록 누락 여부를 모른다고 가정하고 업로드하게 한다. 체크하지 않아도 탐색은 가능하고 이후 결과·성능은 보류된다는 점을 이해하는지 확인한다.
6. overall=9 오류를 안내만 보고 수정하게 한다. 도움 제공 시 무엇을 알려줬는지 기록한다.

현재 상태: **추가 문제 없음 회신 수신 / 과업별 재측정 미확인**. 자동 브라우저 결과는 [개발 검증](../verification/usability-20261025/README.md)에 별도 기록한다. 이후 판단은 [고객별 모델 선택 기준](../model-selection.md)과 [프로젝트 설명](../submission.md)에 연결한다.
