# Harbinger 경험을 연결한 지원 문장

프로젝트 기록에 근거한 개정안입니다. 학력·전직장 성과·다른 프로젝트 경험은 새로 추가하지 않았습니다. 회사 맥락은 [기존 공고·제품 조사](company-research.md)를 따릅니다. 이 문서는 지원서 제출 기록이 아닙니다.

## 기록이 다음 판단으로 이어지도록 — 지원동기

디더블유아이의 시설관리 솔루션을 살펴보며, 쌓인 점검 기록이 다음에 확인할 설비를 고르는 데까지 이어질 수 있겠다고 생각했습니다. 이 생각을 검토하기 위해 합성 점검·정비 이력으로 Harbinger를 만들었습니다. 모델 점수와 함께 원문을 확인하고, CSV를 올려 분석한 결과를 보고서로 내려받는 흐름을 구성했습니다. 개발 과정에서는 예측 시점에 알 수 없던 정답이 평가에 들어가는 문제를 바로잡고, 사용자 의견을 받아 날짜와 기록 완전성 안내를 고쳤습니다. 이 경험을 바탕으로 디더블유아이에서 데이터 처리와 모델 평가를 사용자가 이해하고 활용할 수 있는 서비스로 연결하는 데 기여하고자 지원했습니다.

## 높은 점수보다 다시 확인할 수 있는 결과를 남겼습니다 — 문제 해결 경험

Harbinger를 검증하면서 학습·보정 구간 이후의 고장이 앞 구간의 정답으로 사용되는 문제를 확인했습니다. 관측 기간과 시간 경계를 수정한 뒤 같은 합성 테스트 자료로 다시 평가하자 AUROC가 0.7736에서 0.7696으로 낮아졌습니다. 낮아진 수치를 그대로 공개하고, 미래 기록이 바뀌어도 과거 입력과 정답이 바뀌지 않는지 검증하는 회귀 테스트를 추가했습니다.

이후 생성·학습 시드를 바꾸고 메모 누락과 기록 지연도 비교했습니다. 전체 HGB의 평균 성능은 높았지만 메모를 제외한 모델이 더 나은 실행도 있었고, PyTorch 모델은 메모 누락에 큰 성능 하락을 보였습니다. 이를 통해 모델 구조보다 실제로 사용할 수 있는 기록과 같은 조건의 비교 근거를 먼저 확인해야 한다는 기준을 세웠습니다.

## 이해하기 어려운 지점을 다음 수정으로 연결했습니다 — 개선 경험

평가를 정리한 뒤에는 시설관리 동료와 비전공자 친구에게 검토를 부탁했습니다. 위치로 설비를 찾고 싶다는 의견, 과거 예측을 현재 위험으로 이해한 반응, 자료의 누락 여부를 본인이 확인하기 어렵다는 의견이 나왔습니다. 층·구역 검색과 예측 당시 날짜를 보완하고, 확인할 수 없는 현재 수리 상태는 별도로 표시했습니다. 기록 완전성을 확인하지 못해도 탐색은 가능하게 하되, 이후 고장 여부와 성능 평가는 서버에서 보류하도록 수정했습니다.

수정 후 추가 문제가 없다는 회신을 받았습니다. 과업별 재측정 자료는 없어 작업 시간이나 성공률 개선으로 표현하지 않았습니다. 구현에는 Codex를 활용했으며, 프로젝트 방향과 수용 기준을 정하고 검토 의견을 전달해 결과를 확인하며 개정했습니다.

## 고객의 기록과 업무 기준부터 이해하겠습니다 — 입사 후 포부

입사 후에는 담당 서비스의 데이터 흐름과 고객이 분석 결과를 사용하는 방식을 먼저 이해하겠습니다. 같은 고장이라도 고객마다 기록 기준이 다를 수 있으므로 담당자와 사건의 정의, 기록 시점, 실제 점검 가능한 수량을 확인하겠습니다. 이를 바탕으로 단순한 기준과 모델을 같은 조건에서 비교하고, 선택 이유를 설명할 수 있는 결과를 만들겠습니다.

예측한 날짜 이후의 기록이 아직 충분히 쌓이지 않았거나 고장 기록이 빠졌는지 확인할 수 없다면, 적중 여부를 확정하지 않고 무엇이 더 필요한지 안내하겠습니다. 검증된 결과는 API와 화면으로 연결하고, 사용자가 혼동하는 표현과 입력 오류도 함께 개선하겠습니다. 고객별 모델을 만드는 과정에서 성능 수치, 데이터 조건, 실제 사용 흐름을 함께 확인하는 개발자로 기여하겠습니다.
