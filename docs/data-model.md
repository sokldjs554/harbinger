# 데이터 모델 — 유비스 마스터류 FMS 에서 역추론한 스키마

실제 유비스 마스터의 DB 스키마는 공개되어 있지 않다. 공개된 기능 설명(체크리스트, NFC/비콘 점검, 사진, 메모, 고장수리·자재·장비, 전기·가스·수도·지역난방)에서
"분석에 필요한 최소 테이블"을 역추론했다. 실데이터 연결 시 바뀔 가능성이 높은 지점은 **⚠** 로 표시했다. 코드: `src/harbinger/schema.py`.

## 테이블

| 테이블 | 한 행 | 핵심 열 | 실데이터 메모 |
|---|---|---|---|
| `sites` | 고객사 건물 | `site_id`, `archetype`(정부청사·병원·호텔·오피스), `floors`, `opened` | ⚠ 아키타입은 영업 분류에서 가져오거나 설비 구성으로 추정 |
| `inspectors` | 점검자 | `inspector_id`, `site_id` (+ 합성 전용 성향 3개) | 성향 열은 **실데이터에 없다** — 모델은 쓰지 않고, 품질 피처로 추정한다 |
| `assets` | 설비 | `asset_id`, `category`(12종), `floor`, `zone`, `installed`, `criticality`(1~3), `beacon_id` | ⚠ 설비 분류 체계는 고객사마다 다르다 → 12종으로의 매핑 테이블 필요. 중요도는 없으면 분류 기본값 |
| `inspections` | 점검 1건 | `scheduled_at`, `performed_at`, `method`(nfc/beacon/manual), `dwell_seconds`, `overall`(0/1/2), `chk_<item>`(항목별 0/1/2, 해당 없음은 NULL), `memo`, `photo_count` | ⚠ `dwell_seconds` 는 비콘 체류 로그가 있을 때만. 없으면 품질 피처 일부가 결측(모델은 결측 허용) |
| `workorders` | 고장수리·예방정비·부품교체 1건 | `type`(breakdown/preventive/parts), `opened_at`, `closed_at`, `severity`, `downtime_hours`, `parts_cost_krw`, `description` | ⚠ **"비계획 고장"의 정의가 라벨을 결정한다.** 접수 경로(민원·점검 중 발견·자동 경보)로 구분할 수 있으면 더 좋다 |
| `energy` | 사이트·일 | `electricity_kwh`, `gas_m3`, `water_m3`, `heat_gcal`, `temp_mean_c`, `occupancy_index` | ⚠ 검침이 월 단위면 일별 회귀 대신 월별 회귀로 내려간다. 기온은 기상청 ASOS 로 보강 |
| `latent` | 설비·일 (합성 전용) | `d` 숨은 열화 상태 | **실데이터에 없다.** 오라클 상한 계산에만 쓴다 |

## 라벨 정의

- **y30**: 점검 시점 t 이후 (t, t+30일] 안에 `type=breakdown` WO 가 열렸는가.
- **tte_days / event**: 다음 breakdown 까지 일수. 없으면 데이터 끝에서 중도절단(event=0).
- **label_valid**: t+30 이 데이터 끝 이전인 행만 분류 학습·평가에 쓴다.

점검에서 불량을 발견해 부품교체(parts)로 이어진 경우는 고장이 아니다. 이것은 **의도된 선택**이다: 모델이 맞혀야 하는 것은 "사람이 이미 잡은 것"이 아니라 "놓쳐서 멈춘 것"이다.
그 결과 라벨은 개입(수리) 아래에서 관측되므로 — 모델이 잘 맞혀서 미리 고치면 양성 라벨이 사라지는 — 운영 후 재학습 시 이 효과를 감안해야 한다(`docs/limitations.md`).
