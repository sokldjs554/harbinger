# 한계 — 이 저장소가 증명하지 않는 것

1. **모든 수치는 합성 데이터에서 나왔다.** 생성 모델(`docs/synthetic-generator.md`)이 "메모는 체크리스트보다 먼저 움직인다", "고장은 열화-주도적이다"를 가정하기 때문에, 텍스트 피처의 기여와 전체 AUROC 는 실데이터에서 더 낮을 가능성이 크다. 이 저장소가 보여 주는 것은 **파이프라인·평가 설계·운영 형태**이지 성능 주장이 아니다.
2. **오라클 상한이 존재한다.** 숨은 상태를 그대로 아는 오라클의 AUROC 가 0.8 초반이다. 모델과 오라클의 차이가 "관측 노이즈로 잃은 것"이고, 오라클과 1.0 의 차이가 "돌발 고장"이다. 실데이터에는 오라클이 없으므로 이 분해는 할 수 없다.
3. **라벨은 개입 아래에서 관측된다.** 점검 불량 → 조치가 고장을 막으면 양성 라벨이 사라진다. 모델을 배포해 순찰을 바꾸면 라벨 분포가 또 바뀐다(performative). 운영 재학습에서는 "모델이 지목해 조치한 설비"를 별도 표시해 두어야 한다.
4. **콜드스타트 오프셋의 효과는 작았다.** pooled 모델이 이미 사이트 간에 잘 캘리브레이션돼 있어 경험적 베이즈 오프셋은 Brier 를 거의 바꾸지 않았다. 실데이터처럼 사이트 간 기록 문화 차이가 크면 달라질 수 있고, 그때는 사이트 임베딩(위험 네트)이나 사이트별 재캘리브레이션이 더 유효할 것이다.
5. **생존 모델의 독립성 가정 위반.** 같은 설비의 점검 행들은 서로 독립이 아니다. Cox/AFT 의 표준오차는 과소 추정되며, 여기서는 점추정과 순위 지표(C-index)만 쓴다.
6. **메모 인코더는 합성 한국어에 맞춰져 있다.** 실제 메모는 오타·축약·현장 은어가 많다. 문자 CNN 은 오타에 비교적 강하지만, 실데이터에서는 렉시콘을 현장 용어로 다시 만들고, 사전학습 한국어 모델(네트워크가 허용되면)과 비교해야 한다.
7. **에너지는 사이트 단위다.** 설비 단위 계측(서브미터링)이 없으면 전기 잔차는 HVAC 군 전체의 증거일 뿐 특정 냉동기를 지목하지 못한다.
8. **유비스 하이(환자이송)는 범위 밖이다.** 같은 틀이 적용된다: 이송 요청 1건 = 행, 생존 시간 = 요청→도착 소요, "지연 위험" = 30분 초과 확률, 처방 = 이송원 배치. 요청 텍스트(이송 사유)가 메모 역할을 한다. 데이터 형태가 같아서 피처 빌더와 API 골격을 재사용할 수 있지만 검증은 하지 않았다.
9. **콘솔은 인증이 없고 데모용이다.** 운영 UI 는 FMS 앱 안에 들어가야 하며, 이 콘솔은 API 응답이 현장 언어로 읽히는지를 보여 주기 위한 것이다.
10. **단일 프로세스·메모리 적재.** 사이트 100개 이상이면 피처 저장소를 DB/오브젝트 스토리지로 옮기고 사이트 단위로 읽어야 한다.

## 실데이터로 갈 때 순서 (`docs/real-data-checklist.md`)

가정 1~3 을 먼저 확인하고, 그 다음에야 모델을 튜닝한다. 모델보다 라벨 정의와 점검 품질이 먼저다.
