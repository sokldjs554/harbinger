# 회사 조사 — (주)디더블유아이(DW&I)는 어떤 회사이고, 왜 지금 "AI 분석 서비스 개발자"를 뽑는가

> 이 문서는 harbinger 를 **왜 이 주제로 만들었는지**의 근거입니다. 공고 문구를 그대로 따라간 것이 아니라,
> 회사가 지난 12년 동안 무엇을 팔아 왔고, 어떤 데이터가 쌓여 있으며, 2026년에 무엇을 하겠다고 공표했는지를
> 먼저 조사한 뒤 공고를 다시 읽었습니다. 조사 시점은 2026-10 이고, 출처는 문서 끝에 모아 두었습니다.

핵심 관찰: **이 회사의 데이터는 센서 시계열이 아닙니다.** IoT 센서를 파는 회사가 아니라, **사람이 설비 앞에 가서 체크하고 메모를 적는 행위**를 디지털화한 회사입니다.
그래서 쌓인 데이터는 (1) 불규칙한 시점의 (2) 사람이 쓴 (3) 주관적이고 결측이 많은 (4) 한국어 자유 텍스트가 섞인 점검 기록 + 고장 이력 + 월 단위 검침 에너지입니다.

## 3. 2026년, 회사가 공표한 방향

- 2023 인터뷰: "**빅데이터와 인공지능을 기반으로 설비 수명과 고장을 예측하는 시스템을 개발하고 있다**."
- 2026-04: NIPA 클라우드 공급기업 2년 연속 선정 — "중소기업 시설관리 업무 **AX** 지원".
- 2026-06 수상 기사: "**2026년형 모델은 축적된 데이터를 분석해 장비의 장애를 예측하고 최적의 운영 시나리오를 제시하는 AI 기능을 강화**했다."

즉 공고의 "AI 분석 서비스 개발자"는 추상적인 AI 인력이 아니라, **유비스 마스터 2026년형의 '장애 예측 + 운영 시나리오' 기능을 실제로 만들어 60개 고객사에 붙일 사람**입니다.

## 4. 공고를 다시 읽기 — 각 줄이 실제로 뜻하는 것

| 공고 문구 | 이 회사 맥락에서의 실제 의미 |
|---|---|
| AI 기반 데이터 분석 모델 개발 및 고도화 | 유비스 마스터에 이미 쌓인 점검·고장·에너지 데이터로 **고장 예측 모델**을 만들고, 고객사가 늘어도 성능이 유지되게 하는 것 |
| Python 기반 데이터 전처리 및 분석 | 수기→디지털화된 점검 기록은 더럽습니다. 점검 주기 불규칙, 복붙 메모, 체류시간 0초, 지연 점검. **전처리가 모델보다 중요한 데이터** |
| 머신러닝/딥러닝 모델 설계 및 성능 개선 | 자격요건에 Regression·Classification 을 콕 집었습니다. 분류(30일 내 고장?)와 회귀(에너지 기대치) 둘 다 쓸 자리가 실제로 있습니다 |
| 분석 결과를 API 또는 웹 서비스 형태로 구현 | 분석 노트북이 아니라 **유비스 마스터 앱/웹이 호출할 API**. FastAPI/Flask 우대가 그래서 붙었습니다 |
| **실증 프로젝트 및 고객 맞춤형 모델 개발** | 60개 고객사의 설비 구성·점검 문화가 전부 다릅니다. 정부청사형·병원형·호텔형·오피스형. **신규 고객사는 데이터가 없는 상태에서 시작**합니다(콜드스타트). "실증" = 고객사 한 곳에서 PoC 로 효과를 숫자로 보여 주고 계약으로 연결하는 일 |
| 데이터 시각화 우대 | 시설관리 담당자와 **공공기관 보고서**가 읽을 수 있는 그림 |
| 클라우드(AWS, GCP) 우대 | 유비스 마스터 프로가 SaaS. 모델도 클라우드에서 멀티테넌트로 돌아야 함 |
| 실제 서비스 운영 경험 우대 | 9명 회사. 만든 사람이 운영합니다. 배포·모니터링·장애 대응까지 |

## 5. 그래서 이 회사가 원하는 지원자

1. **혼자서 끝까지 가는 사람.** 데이터 전처리 → 모델 → API → 시각화 → 배포 → 운영을 한 사람이 합니다. 신입/1년차를 뽑는 이유는 비용이지만, 뽑히는 이유는 end-to-end 를 보여 준 사람일 것입니다.
2. **현장 작업자 관점을 가진 사람.** 대표의 창업 서사 자체가 "현장 작업자가 쓰기 어려운 시스템을 바꿨다"입니다. 모델 정확도보다 **"점검자가 내일 아침 어디부터 보면 되는가"**를 답하는 결과물을 더 높게 볼 것입니다.
3. **지저분한 사람-생성 데이터를 다뤄 본 사람.** 센서 데이터 벤치마크(NASA C-MAPSS 류)가 아니라, 체크리스트·메모·이력 같은 데이터를 신호로 바꾼 경험.
4. **고객 맞춤과 콜드스타트를 생각하는 사람.** 범용 모델 하나가 아니라, 고객사별로 적응하되 데이터가 없는 고객사에서도 동작하는 구조.
5. **설명할 수 있는 사람.** 정부청사가 고객입니다. "왜 이 설비가 위험한가"를 점검 기록을 인용해 설명해야 공공 보고서에 들어갑니다.
6. **제품으로 만들어 파는 것을 이해하는 사람.** 매출 20억·상장 목표. "AI 기능 강화"는 영업 포인트이고, 실증 PoC 가 계약을 만듭니다.

## 6. 그래서 harbinger 는 이렇게 설계했다

| 회사가 보는 것 | harbinger 의 답 |
|---|---|
| 센서 없는 설비의 고장 예측 | **사람의 점검 기록(체크리스트 + 한국어 메모) + 고장 이력만으로** 30일 내 고장 확률과 생존곡선을 추정 |
| 더러운 사람-데이터 | 점검 품질 감사(복붙 메모·체류 0초·지연) 를 **피처이자 가중치**로 사용. 메모의 약신호("약간 소음", "미세 진동")를 렉시콘 + 문자 CNN 으로 신호화 |
| Regression · Classification | 30일 내 고장 분류기 · 생존분석(Cox/AFT/이산시간 위험 네트) · 에너지 기대사용량 회귀 → 잔차 이상 |
| 고객 맞춤 · 콜드스타트 | 정부청사·병원·호텔·오피스 아키타입, 사이트 임베딩 드롭아웃, 경험적 베이즈 오프셋, **leave-one-site-out** 평가 |
| 운영 시나리오 제시 | 순찰 우선순위(기대손실 기반, 법정점검 강제 포함) · 설비별 권고 점검 주기 · 점검 인력 예산 하에서의 상위 K |
| 공공 고객의 설명 요구 | SHAP 기여도 + **실제 점검 메모 인용** 으로 "왜"를 보고서 문장으로 |
| API · 클라우드 · 운영 | FastAPI, Prometheus 메트릭, 드리프트(PSI) 모니터, 모델 레지스트리, Docker, Cloud Run / App Runner 배포 구성 |

## 7. 조사에서 확인하지 못한 것 (가정으로 처리)

- 유비스 마스터의 **실제 DB 스키마**는 공개되어 있지 않습니다. 공개된 기능 설명(체크리스트, NFC/비콘, 사진, 메모, 고장수리·자재·장비, 에너지 4종)에서 역추론한 스키마를 `docs/data-model.md` 에 적고, 실데이터 연결 시 바꿔야 할 지점을 표시했습니다.
- 고장·점검 데이터의 **실제 통계**(고장률, 점검 주기, 메모 길이)는 알 수 없습니다. 합성 데이터의 생성 모델을 `docs/synthetic-generator.md` 에 전부 공개했고, 결과 숫자는 그 생성 모델 아래에서의 값임을 README 에 명시했습니다.
- 유비스 하이(환자이송)의 데이터는 이번 범위에 넣지 않았습니다. 같은 생존분석 틀(이송 소요시간 → 지연 위험)이 그대로 적용된다는 점만 `docs/limitations.md` 에 설계로 남겼습니다.
