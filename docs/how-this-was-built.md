# 이 저장소가 만들어진 방식

사람이 방향과 수용 기준을 정하고, 코딩 에이전트가 조사·구현·측정을 실행하는 방식으로 만들었습니다.
숨길 것이 아니라서 커밋 트레일러(`Co-Authored-By`)에 그대로 적혀 있습니다.

## 순서

1. **회사 조사가 먼저였다.** 공고를 읽기 전에 (주)디더블유아이가 무엇을 팔아 왔는지(유비스 마스터·하이, 정부청사 G-FMS), 어떤 데이터가 쌓이는지(NFC·비콘 점검, 메모, 고장수리, 에너지), 2026년에 무엇을 하겠다고 했는지("장애 예측 + 운영 시나리오", 클라우드 AX)를 조사했다. → `docs/company-research.md`
2. **그 다음 공고를 다시 읽었다.** "실증 프로젝트 및 고객 맞춤형 모델 개발"이 핵심 문장이었다. 60개 고객사, 신규 고객사의 콜드스타트, 공공 고객의 설명 요구.
3. **주제를 골랐다.** 센서 시계열 예지보전(흔하다)이 아니라, 이 회사가 실제로 가진 **사람이 쓴 점검 기록**에서 전조를 읽는 것.
4. **합성 데이터의 생성 모델을 먼저 공개하기로 했다.** 결과 숫자가 좋아 보이게 만드는 선택(BETA_SCALE)은 문서에 그 이유와 함께 적었다. → `docs/synthetic-generator.md`
5. 피처 → 모델 → 평가 → 처방 → API → 콘솔 → 배포 구성 → 문서 순으로 만들고, **README 의 숫자는 스크립트가 산출물에서 채우며 CI 가 불일치를 검사**한다(`scripts/fill_numbers.py --check`).

## 사람이 판단한 것

- 처음 생성 모델에서는 숨은 상태를 그대로 아는 오라클의 AUROC 가 0.74 였다. 그 세계에서는 어떤 모델도 차이를 보여 줄 수 없어 열화-고장 결합을 올렸다. **이것이 숫자를 좋게 만드는 선택**이라는 점을 문서에 남겼다.
- 점검 불량 → 조치로 막은 고장은 라벨에서 뺐다. 모델이 맞혀야 하는 것은 "사람이 이미 잡은 것"이 아니라 "놓쳐서 멈춘 것"이다.
- 에너지 잔차가 숨은 열화와 상관이 없게 나왔을 때(첫 버전, 상관 −0.08), 지표를 빼는 대신 생성 모델의 효과 크기가 잡음보다 작았음을 확인하고 효과를 키운 뒤 **그 사실을 적었다**.
- 콜드스타트 오프셋의 효과가 작게 나온 것은 그대로 보고했다.

## 첫 공개 뒤의 비판과 개정

첫 공개 후 "이런 주제는 흔하지 않냐"는 질문이 나왔다. 맞는 지적이었다. 예지보전은 흔한 주제이고, 합성 데이터 위의 AUROC 는 차별점이 못 된다. 그래서 README 에 흔한 부분과 주장하는 부분을 나눠 적었고(§ 흔한 주제 아닌가), 데모의 쓸모를 숫자 나열에서 **사람이 따라가 볼 수 있는 것**으로 바꿨다.

- 과거 재현: 모델이 그 시점에 무엇을 골랐고 실제로 무엇이 고장났는지를 주 단위로 본다. 숫자 하나가 아니라 틀린 주도 보인다.
- 메모 분석기와 What-if: 이 프로젝트의 핵심 주장(메모를 읽는다)을 직접 만져 볼 수 있게 했다. 반대로 숫자가 불리하게 나오는 경우(불량으로 적으면 위험이 내려감)도 프리셋에 넣었다.
- 가정 화면: 결과가 기대는 가정(메모 효과는 생성기에서 온다 등)을 데모 안에 두었다.
- 그 과정에서 드러난 결함도 고쳤다. 점검 1일 뒤 고장난 설비가 계속 1위로 뜨던 문제(시간 의존 피처 갱신), 첫 What-if 가 점검 이후의 실제 이벤트를 섞어 변화량을 오염시킨 문제(마지막 점검 교체 방식으로 변경), 무조건 적용하던 isotonic 이 ECE 를 나쁘게 한 문제(교차적합 선택).
